# 01 — Research: what 12.1 changes in the Cooldown Manager

**Read `tasks/00-AGENT-BRIEF.md` first. It is not optional.**

**Type:** research and reporting only. **You will not write a single line of Lua
in this task**, and you will not edit any file in the repo except your own report.

**Runs in parallel with:** task 02. Stay out of its files and it stays out of yours.

---

## Why this task exists

The live client is **12.0.7 (Interface 120007)**. 12.1 is on the PTR, and
`Gethe/wow-ui-source` carries a `ptr` branch that was last updated 2026-08-07 —
so the next patch is readable *today*, before it ships.

`docs/UPCOMING-PATCH.md` already records some of this from the wiki. The wiki is
Tier 2 on this project and has been **outright wrong** about this exact system:
it lists `overrideSpellID` as a 12.1 addition when our 12.0.7 code already reads
it and works, and it listed the `Cooldown` setters as accepting secret values
when `SetCooldownDuration` demonstrably refuses them.

**Your job is to replace what the wiki said with what Blizzard's source says.**
Where they agree, say so. Where they disagree, say that louder.

## The five questions, in priority order

Answer each one with **evidence pasted into your report** — the file path, the
branch, and the relevant lines. An answer without the lines it came from is not
an answer on this project.

### Q1. The category enum, on both branches

`docs/UPCOMING-PATCH.md` claims `Enum.CooldownViewerCategory` gains five values
in 12.1: `GroupBuff`(4), `SpecAgnosticEssential`(5), `SpecAgnosticTracked`(6),
`EquipSlotEssential`(7), `EquipSlotTracked`(8), on top of the existing
`Essential`(0), `Utility`(1), `TrackedBuff`(2), `TrackedBar`(3).

Report the **full enum as generated on `live`, and the full enum as generated on
`ptr`**, with values. Confirm or correct every name and number above.

Then answer one specific structural question, because task 02 depends on it:

> **Does the generated `Enum.CooldownViewerCategory` table contain anything
> other than `name = <number>` pairs?**

Some WoW enums ship alongside a companion `Meta` table carrying `MinValue` /
`MaxValue` / `NumValues`. Say whether that companion exists for this enum, and
whether it lives **inside** the enum table or beside it under a separate key.
Code that iterates the enum has to know. Quote the generated declaration.

### Q2. `isInvisible` — what does it actually mean?

`CooldownViewerCooldown` reportedly gains `isInvisible` (boolean) in 12.1.
`docs/UPCOMING-PATCH.md` guesses it means "in the data but should not be shown"
and explicitly says to verify before relying on it. **This is that verification,
and a follow-up task is blocked on your answer.**

Find every use of `isInvisible` in Blizzard's `ptr` UI Lua and report what their
own code does with it — which function reads it, what it gates, and whether an
invisible entry is filtered out of a category set or merely drawn differently.

If the field appears in the generated documentation but **nothing in their UI
reads it**, say exactly that. That is a real and useful answer, and it is the
one that would stop us filtering on a field whose meaning we invented.

Also report its secret-value flags, if it carries any.

### Q3. The new cooldown fields, and the flags on the whole structure

Report the complete `CooldownViewerCooldown` structure as generated on **both**
branches, field by field, with types and nilability. `docs/UPCOMING-PATCH.md`
names `equipSlot`, `buffSlot` and `isInvisible` as new — confirm or correct.

Then the question that matters more than the field list:

> **Does any field of `CooldownViewerCooldown`, or any `C_CooldownViewer`
> function, carry a `SecretWhen*` flag on `ptr` that it does not carry on `live`?**

`docs/DECISIONS.md` §13 rests on cooldown IDs staying plain readable numbers in
combat — that is the entire mechanism by which the buff icons work today. If
12.1 makes any of that secret, the feature breaks and we need to know now.
Brief §6 has the flag table.

### Q4. `CooldownViewerSecure.lua`

The `ptr` branch has files absent from `live`:

- `CooldownViewerSecure.lua`
- `CooldownViewerDraggedItemBase.lua` / `.xml`
- `CooldownViewerEditAlertBase.lua` / `.xml`

Read `CooldownViewerSecure.lua` first and report what it does. The specific
worry, from `docs/UPCOMING-PATCH.md`:

> if any of the viewer moves into a secure/protected path, addon interaction
> with it may change.

Concretely, and this is the question to actually answer:

> **`modules/CooldownViewer/BlizzBuffs.lua` finds Blizzard's buff item frames and
> calls `SetPoint` and `SetScale` on them, and hooks `RefreshLayout`. Would any
> of that be blocked, protected, or newly taint-exporting under 12.1?**

Read `BlizzBuffs.lua` and `docs/DECISIONS.md` §13 and §15 so you know what you
are checking against. Report what changed in the item/pool/layout path between
`live` and `ptr`, especially anything touching `RefreshLayout`, the item pool,
or the frames' parentage.

Skim the two `*Base.lua` files and say in one line each what they appear to be.

### Q5. The aura tightening

`docs/DECISIONS.md` §12 records an expectation that in 12.1 the index / slot /
instanceID aura calls will **Lua error** rather than return secrets, and that
the fallback list walk in `modules/CooldownViewer/Core.lua` is "on borrowed time".

Check that against the generated aura documentation on `ptr` versus `live`.
Report the flags on `GetAuraDataByIndex`, `GetAuraDataBySlot`,
`GetAuraDataByAuraInstanceID`, `GetUnitAuraBySpellID`, `GetPlayerAuraBySpellID`,
and `GetUnitAuraInstanceIDs` on both branches, and say plainly whether the
expectation holds, is wrong, or cannot be determined from the docs alone.

## Rules specific to this task

**Do not report a rumour.** Every claim in your report needs a file path and a
branch, or it does not go in. If you looked at the wiki, cite the URL and mark
it as Tier 2 — and check it against the source before you repeat it.

**Do not fix anything you find.** If Q3 or Q4 turns up something that breaks a
feature, that is a finding, not an invitation. Write it in **Noticed but did not
touch** and stop. A code change here would collide with task 02, which is
running at the same time.

**Distinguish "absent" from "unchanged".** If you cannot find a file or a field
on a branch, say which you searched and how, rather than concluding it does not
exist. `gh api` failing is not evidence about the game.

**If the `ptr` branch has moved on to a build past 12.1**, say so with the build
number, because it changes what the comparison means.
